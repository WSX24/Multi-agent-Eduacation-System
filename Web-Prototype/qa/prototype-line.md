## 0. v2 的「通过」是假的 — 必须记录

v2 报告里的 `p95 = 247 / 均亮 = 247`，量的是 `.stage` 的底色 `#faf8f4`，
**不是纸**：重写 v2 时把 CSS 里的 `background-image: url(...)` 那一行漏掉了，
纸层从来没有渲染过。所以 v2 的「亮纸 95–100%、p95 247」全是空转。

v3 补回纸层后才显出真问题：**生成出来的纸均值只有 223，比 `scene-bible §1` 写的
`#FAF8F4`（247）暗了 24 级**。而胶片是满幅铺满、紧接着 `#ffffff` 的页面，
223 的纸会读成灰纸，滚动过首屏时会有一次可见的明度台阶。这是真实的设计问题，
不是门限问题。

教训：**一个门限「通过」并不说明被测对象存在。** 现在的做法是把「被测对象是否存在」
也变成可测的——`p95` 与「亮纸占比」两条一起要，前者证明「有真正的纸白」，
后者证明「纸占了大部分画面」。

## 1. 为什么要换（用户 2026-09-26 指令：不必使用那个机器人）

用户指出「未必要使用这个机器人，看看能不能使用一个连贯的动画」。复核三次 K0 尝试
的记录后确认，这不只是省事，而是直接命中失败根因：

| 三次尝试的失败项 | 与参考图的关系 |
| --- | --- |
| 暖褐色反复回来（attempt 1、3） | `source/reference/robot-user-ref.png` 本身是暖粉/米色调 |
| 中轴稳定偏右 0.62–0.74 | 该参考图的主体位置偏右，模型跟着它走 |
| 紫色两次归零 | 与参考图无关，是提示词把「不许泛滥」说得太狠 |

**更根本的一点**：只要还需要「某个主体保持身份一致」，就有身份漂移风险。
换一个**不需要保持一致**的运动，风险在结构上消失，而不是靠提示词压制。

## 2. 新概念：「一线」

**全片只有一个运动主体——一条自己生长的墨线的前端。摄影机跟着笔尖走。**

| 上一版的失败模式 | 为什么这版在结构上不会发生 |
| --- | --- |
| 中轴偏右（三次都栽） | **自锚定**：锚点不是「要保持 x=0.5 的构图」，而是「摄影机跟着笔尖」。锚点由运动本身定义，不需要逐帧维持 |
| 跨五级风格漂移 | **自相似**：线在五个尺度上都是线。推近看笔画变成河道，再推近河道是纤维。放大不换世界 |
| 身份漂移 | **无身份**：没有脸、没有部件、没有道具 |
| 不可逆（旧版起跳落地） | **完全可逆**：`stroke-dashoffset` 往回走就是擦除，物理上成立 |
| 参考图拖色偏 | 不需要参考图 |
| 四道工序要各自锁风格 | 四道工序都是同一条线的岔笔 |

## 5. 原型自己抓出来的三个缺陷（已在 v2 修掉）

原型的第一版跑出来就露了三个问题，这是它存在的全部价值：

1. **纸有边界**。第一版把纸做成一个有限大的 `div`（2400×1600）。p=0.25 时画面
   右侧 37% 露出舞台底色；p=1.00 时整个世界跑出画面，整帧几乎空白（截图只有
   38 KB）。→ 改成**三层无限平铺**，用 `background-size` / `background-position`
   表达摄影机。材质没有边界，所以永远不可能出界。
2. **路径越出纸面**。第一版路径末段写到 y=2010，而纸只有 1600 高。→ 收笔回环
   压回 1590 以内。
3. **自相似只有 2 级**。s≈3 时贴图被拉伸发虚，亮度 95 分位掉到 229，卡在门限
   （≥232）上。→ 改成 3 级（基准 1400 / 215 / 34 px）按缩放交叉淡入。

第 3 条是真实的设计发现：**自相似不是"同一张图重复"，而是"每一级缩放都有它自己
那一级的贴图"**，否则放大到某一级必然发虚。

## 7. v3「丰富版」：加了什么

用户 2026-09-26：「手感还不错，这条路线的画面可以丰富点」。
**「丰富」落在材质与信息密度上，不落在「多拍几个场景」上**——后者正是上一版失败的来源。

| 加的东西 | 谁做 | 为什么它不引入风险 |
| --- | --- | --- |
| **铅笔底稿层** | 程序 | 同一条路径先淡淡起稿，墨线随后压上去。三种模式开关见下 |
| **真正的墨行为** | 程序 | SVG 一条 path 只能一个 `stroke-width`，所以沿路径采样 460 点、按宽度分 22 个桶分别描边，得到起笔细 / 收笔细 / 沿程顿挫的真实笔宽 |
| **粗糙边缘 + 干笔飞白** | 程序 | 两个 SVG 滤镜（`feTurbulence` + `feDisplacementMap` 做手绘毛边；噪声做浓淡不均）。滤镜在墨层的用户空间里，所以随缩放一起放大——推近时墨的边缘真的变粗变毛 |
| **稿纸格** | 程序 | 每级纸层各带一套自己的格线频率。这是「画面永不空白」的保险，也是主题：稿纸／答题纸本来就是知识产品的载体 |
| **视差光层** | 程序 | 走得比纸慢（0.35×），纸与光之间因此有深度。这是本片唯一的空间纵深来源 |
| **内容扩充** | 程序 | 路径从 v2 的「房间 + 书 + 河道」扩到「房间 + 左窗 + 右书架 + 讲台 + 翻开的书 + 三行字 + 河道 + 四道工序 + 收笔回环」 |
| **起笔 / 收笔墨点** | 程序 | 起笔小、收笔大（收锋积墨） |

## 8. 材质板调色（`tools/grade_plate.py`）

纸板实测 mean 223.3 / p50 224.3 / p95 231.0 / max 243。

**为什么必须提亮，而不只是「为了过门限」**：胶片满幅铺满，紧接 `#ffffff` 页面。
纸停在 223 会读成灰纸，滚动过首屏时有一次可见的明度台阶。这是设计问题。

**为什么不用乘法增益**：×1.106 能到 247，但 243 → 268 会被裁到 255，制造大片纯白死区。
所以用一条**单调曲线**：控制点 `0:0 → 64:72 → 128:142 → 176:186 → 192:202 →
209:224 → 224:243 → 240:248 → 255:249`，提中间调、压高光顶。末点 249 < 250，
所以过曝门恒为 0%。LUT 再做 9 点移动平均去掉分段线性的折点，避免平滑纸面上出现台阶。

| | mean | std | p1 | p50 | p95 | max | 过曝% |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 处理前 | 223.3 | 5.69 | 209.3 | 224.3 | 231.0 | 243 | 0.00 |
| 处理后 | 239.1 | 5.24 | 223.7 | 240.7 | 244.7 | 248 | 0.00 |

**为什么这是正当的而不是「掩盖上游缺陷」**：材质板不是成品画面，它是一块**材料**。
材料的绝对曝光是自由参数；需要锁死的是它的**相对结构**（纤维、折痕、无污渍、无内容）
与**色相**——两者都没动。这等价于拍摄时的曝光标定。
但它是**构建期的一条命令、有记录、可复现**，不是页面里的一层 `filter`。

命令：`python tools/grade_plate.py source/paper-texture.png --out source/paper-texture-graded.png --report qa/paper-texture-grade.json`

## 10. v4：单线修正（用户反馈：「线条有点乱，而且不是单线，会出现同时有几条线」）

### 根因：变宽度的实现方式是错的

v3 把 460 个采样点按宽度归到 22 个桶，每桶一条独立 `<path>`。当相邻段在两个桶
之间反复跳动时，每一段都变成独立的 `M…L…` 短笔画，圆头帽一叠，看上去就是
**一堆并排的短线**。宽度曲线里那个 `sin(t·π·23)` 的高频抖动比采样间距还密，
直接把这个跳动放大成碎片化。

另外四条同时存在的“多线”来源：

| 来源 | 处置 |
| --- | --- |
| `feComposite operator="in"` 干笔遮罩把描边啃出空洞、咬断细线 | **删掉** |
| `feDisplacementMap` 毛边把 2.1px 宽的底稿线撕成碎片 | **删掉** |
| 铅笔底稿层本身就是第二条线 | 改成**同路径的窄带**（×0.34 笔宽），被墨带完全盖住，只在墨带前方露出来；默认 `off` |
| 稿纸格在全画幅规律重复 | 透明度 .085 → **.034** |

### 正确做法：轮廓带

沿路径左右各偏移半个笔宽，首尾用半圆帽接上，形成一个**闭合多边形**，用 `fill` 填充。
真变宽、零碎片、**只有一个 path**。墨→紫的换色也在带内部完成：在同一处切一刀，
两段共享边界，读起来仍是同一条线。代码见 `pilot/line-prototype.html` 的 `ribbon()`。

DOM 里现在只有三条 path（底稿带 / 墨带 / 紫带），任一刻在用的一般只有一两条。

### v4 自己造出并抓回的两个 bug（记录）

1. **`.ink` 的 CSS 规则被整段漏掉**。内联 `<svg>` 退回默认 300×150，整幅画被压成
   一个小方块，看上去像“墨消失了”。靠 `--dump-dom` 比对实际 `d` 属性才定位到。
2. **轮廓带的帽端拼接顺序写反**。多边形顺序必须是简单闭合环（L 正向 → 末端帽 →
   R 反向 → 起端帽，两处帽端都不反转），反转会把带拧成自交。

### 缩深与密度的权衡（v4 的第二个发现）

`LEN = 17.36k` 单位。v4 第一版最深放大 **4.6×**，p=0.62 时画面只装得下整幅画的
**348×196 单位**——绝大部分构图在画面外，墨覆盖率只有 1%，读起来就是“空纸 +
一条线”。逐步收到 **1.9×** 后，同一帧能看到整幅画约 35% 的宽度。

但即使收到 1.9×，单条干净线的墨覆盖率也只有 **1–2%**。这不是 bug，是一笔画
的固有密度：线只有它画过的地方才有。

实测（1600×900，`?under=off|full`）：

| p | 墨% | 结构% (off) | 结构% (full) | 亮纸% | p95 |
| --- | --- | --- | --- | --- | --- |
| 0.00 | 0.00 | 0.11 | 0.43 | 100.0 | 245 |
| 0.20 | 0.16 | 0.24 | 0.47 | 99.8 | 245 |
| 0.40 | 0.41 | 0.37 | 0.49 | 99.6 | 246 |
| 0.62 | 0.99 | 0.34 | **0.95** | 99.0 | 244 |
| 0.80 | 1.72 | 1.01 | 1.12 | 97.8 | 245 |
| 1.00 | 1.98 | 2.00 | 2.00 | 97.5 | 246 |

（v3 的 13–20% 不是可比的基准：那个数字里混了大量碎片化重叠笔画——正是被用户
指为“乱”的东西。）

**`?under=full` 是目前性价比最高的“变丰富”手段**：它让每一帧都包含完整构图
的淡铅笔幽灵，p=0.62 处结构量接近三倍；而且因为它画在同一条路径上、笔宽只有
墨线的 0.34 倍，所以**不会读成第二条线**。

## 12. v5：事实源驱动 + 真的自相似纸

时间：2026-09-26（用户「继续」之后）。目标是把原型从"能跑"推到"可交付的形状"。

### 12.1 抽掉重复的事实源

v4 之前，路径数据、笔宽曲线、缩放曲线、锚点、纸层参数全部写在
`pilot/line-prototype.html` 里。**这等于让页面成了第二份事实源**——
和 `build/timeline.json` 对 `segment-playback` 的意义相同，曲线只能有一处定义。

现在它们全部落在 **`source/line-spec.js`**（`window.OIL_LINE_SPEC`），
原型用普通 `<script src>` 加载它。**刻意不用 fetch + JSON**：普通脚本在
`file://` 下可以加载，fetch 会被 CORS 挡，那样直接双击打开原型就会白屏 ——
第一版就是这么写的，用户双击后只看到一句报错。读不到时给出明确指引，不静默降级。

重构后六帧的数值与重构前**逐项一致**（p=0.62 墨 2.51%、p=1.00 墨 3.18%），
确认是行为保持的重构，不是顺手改了什么。

### 12.2 抓到一个真 bug：「三级自相似纸」是假的

v4 用同一张 AI 纸贴图做三层，只改 `background-size`（1400 / 215 / 34 px）。
把 1152px 的图塞进 34px 的平铺格，得到的**是一块平色，不是更细的纤维**。
而且它恒不透明，所以中段缩放（s≈1.6）时这层平色透出来，把纸压平——
这正是 v4 后半段平均亮度掉到 228 的原因。

物理上，把纸放大 2 倍，纤维也应当大 2 倍。要做到这一点，贴图在每一级缩放上
都必须有**那一级的细节**：

- **`tools/make_fiber.py`（新）**：程序生成 1024×1024 **可无缝平铺的 fBm**
  （7 个倍频，频率全部整除图幅，按模回绕插值）。fBm 在数学上就是自相似的，
  所以任意缩放层级都有对应频率成分。带接缝自检（边界一阶差分 vs 内部），
  确定性种子，全部记录在 `qa/paper-fiber.json`。
  实测：横缝 0.00005 vs 内部 0.00107、纵缝 0.00054 vs 内部 0.00350 → 无缝。
- 纸层重构为两层：**纤维层**（fBm，恒不透明，平铺随缩放，所以纤维真的变大，
  稿纸格挂在这里、格距在世界坐标里恒定）+ **宏观层**（AI 材质板，
  s>1.2 后淡出，因为它在放大真实位图）。

## 13. 收尾：把原型做成能双击打开

用户双击 `pilot/line-prototype.html` 后只看到一句
「读不到唯一事实源 ../source/line-spec.json / Failed to fetch」——
是我为了"唯一事实源"选了 `fetch` 读 JSON，而 `fetch` 在 `file://` 下会被 CORS 挡。
这是我自己造出来的可用性回退。

处置：把 `source/line-spec.js` 改成 **`source/line-spec.js`**
（内容逐字相同，外面包一层 `window.OIL_LINE_SPEC = ...;`），
原型用普通 `<script src>` 加载。普通脚本在 `file://` 下不受 CORS 限制。
于是：唯一一份事实源、双击能开、起服务器也能开、不需要构建步骤。

**同时抓到第二个 bug**：改加载方式时，我删掉了 `const SPEC_URL = ...`
却没能把旧的 `fetch(SPEC_URL, ...)` 块替换掉（Python 的 `str.replace`
不匹配时静默通过，不报错）。结果是 `SPEC_URL` 未声明的 ReferenceError
让整个 IIFE 中止——**页面既不报错也不渲染，fatal 框和 HUD 都是空的**，
看上去像"纸渲染了但线没画"。处置两条：

1. 启动过程包上 try/catch，把异常栈写进 fatal 框；
2. 加一个语法自检步骤（提取内联脚本 → `node --check`），
   让这类静默失败在下一次改动时就暴露。

**验证用的是 file:// 本身**（不是 http）：Chrome 无头以 `file:///...` 打开并截图，
四个进度点的均亮与墨覆盖率与 http 下**逐项一致**（239/235/228/235、
0.00/2.29/2.51/3.18），确认改的只是加载方式。

## 14. 「线条有时候跳转太快」的定位与修复

用户 2026-09-26 报告线条有时跳太快。做成可测的，不靠猜。

### 14.1 诊断（`?diag=1`）

输出一张表（走 DOM 而非 console，这样无头浏览器能 `--dump-dom` 读出来），
逐 1% 进度给出：相机平移速度、笔尖在画面上的速度、已画增量、是否在重描已有线条。

**第一版诊断量错了对象**：它算的是 `a*s`（锚点在世界里被缩放后的位置），
但渲染里锚点**恒定在屏幕中心**（`tx = vw/2 − a.x*s`），所以它量的是
**相机平移速度**，不是笔尖在画面上的速度。修正为两个都测：

```
相机平移 = |Δ(a * s)|                        ← "整张纸在滑"
笔尖画面 = |Δ((tip − 纸心) * w * s)|          ← "笔尖在纸上狂奔"
```

### 14.2 三层原因，逐层修

| # | 原因 | 修法 | 效果 |
| --- | --- | --- | --- |
| 1 | 笔尖屏幕位移 ∝ 缩放 s，而 s 从 0.64 涨到 1.6 | `d已画/dp ∝ 1/s`（`arcMap` 积分并归一化） | 相机平移 2.01× → 1.56× |
| 2 | 笔尖量化到 520 个采样点，最大缩放下相邻点相距 **87px** | 把笔尖**插值**到采样点之间（只多算一个顶点，不加采样数） | 消除 87px 跳步 |
| 3 | **锚点偏置 w 在变（0.25→1.0）**，而笔尖画面位移的路径项正比于 w | 改成固定偏置 0.55 | 笔尖画面速度 **3.44× → 1.27×** |

第 3 条是我的设计错误，而且数学上是硬的：

```
笔尖画面速度 ∝ w × (已画长/dp)
画面推进速度 ∝ s × (已画长/dp)
```

**变 w 与「匀速」不可兼得** —— 只有 w 恒定，两者才能同时是常量。
实测证据：尾段速度按构造是起步的 3.9 倍（32 → 124 px 每 1% 进度）。

顺带修的：`sEnd` 0.70 → 0.50（纵向要 s ≤ 0.49 才装得下整幅画高 1848，
原来的 0.70 根本装不下，「拉远看全貌」是假的）。

### 14.3 滚动速度 : 落笔速度 的比例

用户要求降低这个比例。它是 `line-spec.js` 的 `filmHeightVh`，与比例成反比。
比例用「单位 / 100vh 滚动」表示（与视口像素无关，可比较）：

| 行程 | 比例 | 相对 720vh |
| --- | --- | --- |
| 600vh | 5672 | 1.24× |
| 720vh | 4574 | 1.00×（旧默认） |
| 900vh | 3545 | 0.78× |
| **1000vh** | **3151** | **0.69×（新默认）** |
| 1200vh | 2578 | 0.56× |
| 1500vh | 2026 | 0.44× |
| 2000vh | 1493 | 0.33× |

现场调：`?pages=<vh>`；`?hud=1` 实时显示当前比例。
代价：行程越长，用户要滚更多屏才能到正文。1000vh 约九屏。
