# 教学多智能体 Prompt 模板库

一套可复用的 Prompt 模板库（角色扮演型 + Few-shot + CoT），供教师 / 助教 / 督学 / 答疑四类 Agent 直接调用组装 Prompt。

## 快速开始

### 1. 安装（推荐）

```bash
pip install -e .    # 可编辑安装：把模板库注册为本地包
```

安装后，**任意目录**都能 `from prompt_builder import PromptLib`，不再需要手动加 `sys.path`。

> 不安装也能用：在调用文件顶部加
> ```python
> import sys
> sys.path.append(r"C:\...\PromptTemplate")
> ```
> 再 import 即可。

### 2. 使用

```python
from prompt_builder import PromptLib

lib = PromptLib()   # 不传路径，自动定位到模板库目录

prompt = lib.build(
    "teacher",
    {"学科": "初中数学", "知识点": "因式分解", "学生水平": "基础"},
    fewshot=True,          # 自动拼接同名 fewshots/teacher.yaml
    cot="math_steps",      # 追加显式分步 CoT
)
print(prompt)
```

### 3. 运行演示 / 测试

```bash
python prompt_builder.py          # 内置演示
python test_prompt_builder.py     # 冒烟测试（也可 pytest）
python demo_course_flow.py        # 教师 Agent 完整链路：规划 → 门控 → 单元渲染
python eval_planner.py --self-check   # 离线校验 Few-shot 是否合规（不调 API）
python eval_planner.py -n 3 --case math --retry 1   # 真实模型评测：M1 规划
python eval_unit.py --self-check                   # 离线检查 M2 prompt 组装
python eval_unit.py -n 2                           # 真实模型评测：M2 单元渲染
python eval_sprint.py --self-check                 # 离线检查 M3 prompt 组装
python eval_sprint.py -n 2                         # 真实模型评测：M3 短周期速成
python probe_same_topic.py                         # 同题撞车探针
python eval_ablation.py -n 3                       # Few-shot 消融实验
python eval_teacher.py -n 1                        # 真实模型评测：讲授者四档分支
python eval_assistant.py --self-check                # 离线检查助教用例
python eval_assistant.py -n 2                        # 真实模型评测：助教判分
python quality_gate.py                             # 照抄检测器自测
```

## 真实模型评测

`eval_planner.py` 把模板里的约束变成 18 项可判定断言，而不是靠肉眼看输出。

| 断言组 | 内容 |
|--------|------|
| **H1 规划期不出内容** | 无讲解/例题/课件泄漏、学生视图简短、5 小节齐全、全部 `lesson_status=pending` |
| **H2 YAML 可用** | 可被 `yaml.safe_load` 解析、无省略写法（`...` / `[…]` / `{…}`） |
| **结构完整性** | 章/单元 id 命名规范、首章无前置、门控链可执行、测验覆盖本章单元 |
| **工期口径** | 章课时=单元之和、`net_hour_budget` 算对、净课时不超预算 |
| **粒度与作业** | 单元 0.5~3 课时、每单元作业 3~5 题 |
| **非照抄** | 单元标题与 Few-shot 示例的重合率 < 50% |

### 评测用例

| 用例 | 学科 | 用途 |
|------|------|------|
| `math` | 初中数学 | 主路径 |
| `physics` | 初中物理 | 跨学科泛化 |
| `bio` | 初中生物 | **与 Few-shot 同题，照抄回归用例** |

### 实测发现（v1.0 → v1.1）

共发现 4 个真实缺陷并修复，评测通过率 71/72 → 72/72：

| # | 问题 | 根因 | 修复 |
|---|------|------|------|
| 1 | **同题时 100% 照抄 Few-shot**（3/3 逐字节复现示例） | 示例被当成「答案模板」而非「格式模板」；表头写的是「请严格模仿其风格与格式」 | 表头改为「仅演示格式，禁止照搬学科/章节/数值」+ 示例改用别的学科 + 后端重试闸门 |
| 2 | 章 `estimated_hours` ≠ 单元之和 | 模板从未定义 `estimated_hours` 含不含缓冲，规范有歧义 | 新增「课时计量口径」小节，明确章课时=单元之和 |
| 3 | 净课时排满容量，零缓冲（18h/18h） | 预算需多步算术，LLM 不可靠 | 强制先算出 `net_hour_budget` 写成字段再分配，并给算例 |
| 4 | 单元粒度越界（3.5 课时） | 只在能力边界里写了「禁止」，没让模型输出前自检 | 输出纪律增加逐项自检规则 |

H1（规划期不出内容）与 H2（YAML 可解析、无省略写法）**一次通过**，未发现缺陷。

### 照抄问题的最终处理：重试闸门

指令层的修复不具备确定性——`bio` 用例首轮仍 3/3 照抄。因为照抄是**可程序化检测**的，
最终靠后端闸门兜底：

```bash
python eval_planner.py -n 3 --case bio --retry 1
# 首轮 3/3 照抄 → 回投问题后 3/3 修正 → 54/54 通过
```

这跟门控是同一个架构模式：**LLM 负责声明，后端负责校验，校验不过就回投重试**。
不能指望提示词把不确定的模型行为变成确定行为。

## 真实模型评测：M2 单元渲染

M2 是学生实际看到的那一层，它有一句最需要证伪的话：**依据学情数据动态调整难度**。
`eval_unit.py` 用**差分测试**验证它：同一个单元、同一个学生水平，**只改上一章成绩**，
看输出是不是真的不一样。

### 五个用例

| 用例 | 上一章成绩 | 期望行为 |
|------|-----------|---------|
| `low` | 45% | 降档，补前置薄弱点 |
| `mid` | 72% | 保持既定难度 |
| `high` | 92% | 升档，加变式与综合 |
| `nodata` | 无数据 | 如实说明「未做调整」，不得假装调过 |
| `noex` | 45% + 不出例题 | 例题模块改写为「不提供例题」，其余照常 |

### 实测结果（`-n 2`，10 次调用，116/116 通过）

差分相似度是核心指标——**越低说明自适应越真实**：

```
low vs mid   正文相似度 0.27
mid vs high  正文相似度 0.26
low  vs high 正文相似度 0.23
```

三档低于 0.3 的相似度，说明同一单元在不同学情下产出的是**实质上不同的教学方案**，
而不是换个措辞。具体表现：降档时课件大纲里多出一页「P2 前置补救」，升档时例题改为带情境的变式题。
而且每档的【难度调整说明】都引用了真实数字（如「正确率 45%，低于 60%，执行降档」），
未出现「根据学情」这类无法审计的空话。

### 另一个被证伪的风险：跨学科污染

M2 用 `fewshot="teacher"` 复用讲授者的 5 模块风格，而那份 Few-shot 里是**初中数学因式分解**范例，
渲染的却是**初中生物光合作用**单元——很可能把数学内容漏进生物课。
实测 10/10 未出现任何污染（`H5` 检查），说明 prompt_builder 中那句
「示例仅用于演示格式，禁止照搬学科/内容」确实起了作用。

## 真实模型评测：M3 短周期速成

M1/M2 的约束是「必须做到什么」，M3 的约束是**反向的**——「必须不做什么」：
不设复习节点、不设解锁门控，且**不得在紧时限内硬塞内容**。

### 四个用例与时限压力测试

同一学习目标，只改可用时限；再加一个「1 天 + 巨大目标」的用例看它会不会硬塞。

| 用例 | 可用时限 | 学习目标 |
|------|---------|---------|
| `d1` | 1 天 | 欧姆定律 + 串联电路计算 |
| `d3` | 3 天 | 同上 |
| `d7` | 7 天 | 同上 |
| `overload` | 1 天 | 初中电学**全部**（欧姆定律+电功率+焦耳定律+家庭电路） |

### 发现：时限口径未定义，模型把「1 天」当成 24 小时

第一版检查用 1天=24小时折算，结果模型给 1 天排了 **8 小时**内容 + 23 道题却「合法通过」。
根因跟 M1 的「章课时含不含缓冲」是同一类漏洞：**模板从未定义「1 天」是多少小时**。

修复：在模板中写明 **1 个学习日 = 最多 3 小时有效学习时间**，里程碑用时只写小时不写天，
且总用时不得超时限折算的小时数。改完后 `H3` 从「被绕过」变成真约束。

### 发现：以「时间充裕」为由加题

改完时限口径后，模型拿到 21 小时预算就加题，5 个里程碑出了 **26 道**随堂练习（规则是 2~3 题/里程碑）。
输出纪律里补上「不得以时间充裕为由加题」，并把校对器改成**逐里程碑**判定而非总数。

### 实测结果（`-n 2`，8 次调用，144/144 通过）

```
  用例        时限    正文   里程碑   随堂   测验
  d1         1天   2828      4     10     8
  d7         7天   3019      5     15     8
  overload   1天   2441      3      9     8
```

三条关键结论：

1. **两条反向禁令 8/8 零违反**——没出现任何复习节点或解锁语义。
2. **1 天不再超量**：`d1` 只排 4 个里程碑、总用时 ≤3 小时；`overload`（巨大目标 + 1 天）
   反而最克制（3 个里程碑、2441 字符），并明确写出「主动舍弃：并联电路、动态分析、电功率与电热」。
3. **时长不改变体量，只改变节奏**：`d7/d1` 体积比仅 1.07。这是对的——目标相同时
   长时限不该塞进更多内容。真正要守的是「1 天不得比 7 天更重」，而不是「7 天必须更多」。

## Few-shot 消融实验：它到底该不该存在？

既然 Few-shot 会引发「同题换数字拄袭」，那是不是干脆全删？`eval_ablation.py`
用数据回答：三个模板各跑「带 / 不带 Few-shot」，比格式合规率（已排除「照抄/污染」
这类无 Few-shot 时白送分的检查）。

> 实验全部使用**跟 Few-shot 不同学科的用例**，否则拄袭会污染对比结果。

### 结果

| 模板 | 带 Few-shot | 不带 | 判定 | 处置 |
|------|-----------|------|------|------|
| `teacher` | 100% | 90.9% | 提升 9.1pp（模块会缺失） | **保留** |
| `teacher_planner` | 100% | 94.6% | 提升 5.4pp（YAML 会解析失败） | **保留** |
| `teacher_unit` | 100% | 100% | 毫无贡献 | **已删除** |
| `teacher_sprint` | 100% | 79.5% | 提升 20.5pp（里程碑/用时列/题量全崩） | **保留** |

`teacher_unit` 补测到每条件 5 次（共 15 样本），仍全部 100%——删除后
prompt 从 2159 降到 **1406 字符（省 35%）**，且同题撞车拄袭风险归零
（`probe_same_topic.py` 复验：特有算式命中由 4 处降为 **0**，相似度 0.07）。

### 结论：Few-shot 的价值取决于任务类型

- **结构化输出任务**（要吐精确的字段名与层级）——Few-shot 几乎不可替代。
  它用示例传达 schema，比文字描述精确得多；去掉后 YAML 会解析失败。
- **已用编号分节说清格式的任务**——模板文字就够了，Few-shot 是纯开销。
- 而对无贡献的模板，删掉是**双赢**：既省 token，又消除拄袭面。

四个模板全部做过消融，**只有一个该删**。

### 保留 Few-shot 的两个模板怎么办

它们确实在挣工资，不能删，所以拄袭风险只能靠两道防线：

1. 拼接表头的「禁止照搬学科/内容」禁令（已有，实测约 2/3 有效）
2. **后端拄袭检测 + 重试闸门**（M1 已验证 100% 兜住），需推广到 M3

### ✅ 已解决：同题撞车 → 改用「骨架示例」

重试闸门对同题撞车无效（0/3），所以改为**消除撞车源**。两个候选实测对比
（每条件 3~5 次，跨学科用例测格式、同题用例测照抄）：

| 条件 | 跨学科合规 | 同题合规 | 同题照抄(处) | 最长重合 | prompt |
|------|-----------|---------|-------------|---------|--------|
| current 完整实例 | 100% | 100% | **18.3** | **105 字** | 3348 |
| none 不用示例 | 81.4% | 76.7% | 0 | 0 | 1486 |
| A 非学科主题 | 100% | 98.0% | 0 | 0 | 2882 |
| **B 骨架示例** | **100%** | **98~100%** | **0** | **0** | **2487** |

A 与 B 测量打平，定夺标准不是数字而是**保证的性质**，故选 **B**：

| 判据 | A 非学科 | B 骨架 |
|------|---------|--------|
| 保证性质 | 概率性（主题只是「没人问」） | **结构性（没有内容可抄）** |
| 失败模式 | 示例主题漏进输出 | 漏出 `<占位符>` |
| 可否程序化检测 | 需维护领域词表（脆弱） | 正则 `<[^>]+>` 一条搞定 |
| prompt 体积 | 2882 | **2487（省 14%）** |

骨架示例的设计要点：**数量具体、内容抽象**——真列 3 个里程碑、每里程碑 2 题、
5 道测验题（数量约束仍有示范），但所有题目与讲解都是 `<占位符>`。
实测占位符泄漏 0/6、跨学科合规 144/144、prompt 较完整实例省 26%。

### 骨架示例是否推广到其它模板：实测结论是「不推广」

`sprint` 上成功不代表通用。对另外四个模板逐一对比（`eval_skeleton_rollout.py`）：

| 模板 | 完整实例 同题重合 | 骨架 同题重合 | 骨架 跨学科合规 | 结论 |
|------|-----------------|--------------|---------------|------|
| `teacher_planner` | 164 字 | 137 字 | 96.1%（原 100%） | ❌ 格式下降，不改 |
| `teacher` | 22 字 | 0 字 | 100% | ⏸ 现用本就不抄，无需改 |
| `assistant` | 16 字 | 0 字 | 100% | ⏸ 现用本就不抄 |
| `supervisor` | 0 字 | 0 字 | 100% | ⏸ 现用本就不抄 |

> ⚠️ **测试设计教训**：最初把「同题」用例的输入设成与示例**完全相同**，
> 结果 `teacher_planner` 量出 1236 字重合——但输入相同时「正确答案本来就相似」，
> 那不是照抄证据。改成「同知识点 + 扰动一个应改变内容的参数」（5周→2周）后，
> 同一条件降到 164 字，**虚高约 8 倍**。
>
> 另需区分两个不同指标：**「可抄片段长度」**（示例自身有多少内容可被抄走）
> 与 **「实际照抄长度」**（模型真抄了多少）。二者不可混用。

### 历史记录：重试闸门为什么救不了同题撞车

`quality_gate.py` 是生产级闸门（校验 + 照抄检测 + 回投重试），但实测它
**对 M1 有效（3/3 救回）、对 M3 同题无效（0/3）**。根因：

> 重试改不掉上下文里的示例。M1 抄的是章节名，换个名字就行；
> M3 的请求主题**就等于**示例主题，模型被告知「别抄」之后手里还是只有那一套。

而且实测**最终输出的相似度反而更高**（0.54 → 0.61）——重试只是在原地打转。

所以这个问题的解法不是加强闸门，而是**消除撞车源**。两个候选方向：

| 方案 | 做法 | 取舍 |
|------|------|------|
| A 换成非学科示例 | 示例改用「整理书包」这类无人会问的主题 | 彻底消除撞车，但教学风格的示范力可能下降 |
| B 改成骨架示例 | 示例只留结构与字段占位符，不含真实内容 | 从根源杜绝照抄，但题量等数量约束失去具体示范 |

**该实验已完成，结论见上节「✅ 已解决：同题撞车 → 改用「骨架示例」」**——
A/B 测量打平，选 B 的理由不是数字而是保证的性质（结构性免疫 > 概率性）。

## 助教 Agent（assistant）真实评测

`eval_assistant.py` 与其它评测器不同：它的重点不是「格式对不对」，而是**判分对不对**。
做法是构造**已知正确答案的用例**（同一道题、只改学生答案），检查判定与得分是否落在预期区间。

### 判分分辨力（每例 2 次）

| 用例 | 学生答案 | 模型判定 | 评价 |
|------|---------|---------|------|
| 全对 | 完整含方向 | 对 / 满分 | ✅ |
| 漏单位 | `F浮 = 6 - 4 = 2` | 部分正确 | ✅ 且指出了单位问题 |
| 符号错 | `F浮 = 6 + 4 = 10 N` | 错 / 0 分 | ✅ 且归因到「应相减」 |
| 白卷 | （学生未作答） | 错 / 0 分 | ✅ 合理 |
| 答非所问 | 「题目好难，我不想做」 | 错 | ✅ |
| **字段缺失** | （空字符串） | **入口预检拦下，不调用模型** | ✅ 见下 |

### ⚠️ 最重要的发现：学生答案为空时，模型给了满分

实测（未加预检前）：把「学生答案」留空，模型输出

```
1. 【得分】10/10
2. 【答案判定】对
6. 【置信度】高
3. 【错误分析】无错误。你正确使用了「称重法」求浮力……
   并正确标注了方向竖直向上。
```

**学生一个字都没写，却拿到满分**，而且模型**编造了不存在的内容**（「你正确标注了方向」）——
它把旁边的「参考答案」当成了学生答案。只要系统某次没把作答传进来，学生就白拿满分。

模板里其实早已写明「任一项缺失不得猜测，直接标低置信度」，**模型照样无视**。
所以这一项不再交给模型，改由 `quality_gate.blank_inputs()` 在**调用前**拦下：

```python
blanks = blank_inputs(lib, "assistant", variables)
if blanks:
    raise ValueError(f"缺少必要输入：{blanks}")   # ['学生答案']
```

链路里请用强制版，一行接入且行为统一：

```python
from quality_gate import require_inputs

require_inputs(lib, "teacher_unit", variables)   # 缺项直接 ValueError
```

`demo_course_flow.build_unit_prompt` / `build_planner_prompt` 已接入，
因此「输入缺失」在 M1/M2/助教所有调用点都是同一个确定性行为。

这再次印证本项目的架构结论：**能用后端确定性拦住的，就别指望提示词**。

## 顺带修掉的一个真缺陷：`assistant` 拿不到要批改的题

`templates/assistant.yaml` 原版**没有承载「要批改的题」的段落**——模板让模型
「批改学生作答」，却从不把作答传进来（`{{错题}}`/`{{学生答案}}`/`{{参考答案}}`
在文档里标着「（预留）」，从未接进任何模板）。

该缺陷一直被**照抄行为掩盖**：旧的示例表头写「请严格模仿其风格与格式」，
模型会把示例里那道题抄来批改，看起来像在工作。表头改成「禁止照搬」后立刻暴露
（模型开始反问「请提供题目」）。已补上【本次批改任务】段，并写入
「任一项缺失时不得猜测，直接标低置信度」。

> 这说明「修掉照抄」不只是消除一个缺点——它还能**揭穿被照抄掩盖的功能缺陷**。

## API 说明

### 初始化

```python
lib = PromptLib()        # 默认：自动定位到模板库目录（pip install 后推荐）
lib = PromptLib('.')     # 或显式指定模板库目录
```

### build 方法

```python
lib.build(role, variables=None, fewshot=True, cot=None, fewshot_count=None) -> str
```

| 参数 | 说明 |
|------|------|
| `role` | 模板名：`teacher` / `teacher_planner` / `teacher_unit` / `teacher_sprint` / `assistant` / `supervisor` / `qa` / `system_base` |
| `variables` | 变量字典，填充 `{{占位符}}`（未提供的变量会原样保留，便于自查） |
| `fewshot` | `False` 不加示例；`True` 自动用同名 fewshot；传字符串指定其它 fewshot（如 `"teacher"`） |
| `cot` | CoT 片段名：`zero_shot` / `math_steps` / `self_check`；`None` 不加 |
| `fewshot_count` | 最多拼接几个示例 |

辅助方法：`list_roles()` / `list_fewshots()` / `list_cot()` / `missing_vars(role, variables)`。

## 教师 Agent 的三种任务模式

教师 Agent 不是单一角色，而是三个可独立调用的任务模式。**核心是「规划」与「渲染」分离**：
长周期任务先出骨架，单元解锁时才按需生成内容，避免方案微调导致已生成内容作废。

| 模式 | 模板名 | 触发时机 | 产出 | 关键约束 |
|------|--------|---------|------|---------|
| M1 规划 | `teacher_planner` | 开课时一次 | 章→单元骨架 + 工期 + 门控 | **只出骨架，禁止出内容** |
| M2 单元渲染 | `teacher_unit` | 每章解锁后 | 单单元讲解 + 课件大纲 + 作业 | 一次只渲染一个单元，依学情调难度 |
| M3 短周期速成 | `teacher_sprint` | 即时 | 方案 + 内容 + 结束测验，一把出 | 无复习、无门控、一次性 |
| （单次讲授） | `teacher` | 无课程上下文时 | 5 模块知识讲解 | 按 `{{学生水平}}` 分支 |

### 两段式渲染与门控

M1 输出分两部分：

1. **学生视图**——自然语言，给学生和教师看（阶段地图、时间安排、解锁规则）。
2. **系统蓝图**——合法 YAML，供后端解析。关键字段：

```yaml
unlock:
  type: after_chapter      # 门控：上一章测验达 min_score 才开启
  chapter: ch01
  min_score: 60
units:
  - id: ch01-u1
    lesson_status: pending  # 内容尚未生成，解锁时由 M2 按需渲染
```

> ⚠️ 门控是**后端硬约束**，提示词只负责声明条件。模板已显式禁止模型自行判定学生是否通过——防越权幻觉。

### 门控参考实现

`demo_course_flow.py` 实现了这条契约，可直接抽出来用或当参考：

| 函数 | 职责 |
|------|------|
| `parse_blueprint(llm_text)` | 从 M1 输出切出 YAML 并解析，**同时校验所有 `lesson_status` 必须为 pending**（防模型在规划期偷跑内容） |
| `can_unlock(course, chapter_id, progress)` | 按 `unlock` 字段判定该章是否解锁，返回 `(bool, 原因)`，原因可直接展示给学生 |
| `course_status(course, progress)` | 输出整门课的关卡地图 |
| `build_unit_prompt(lib, course, chapter_id, unit_index, progress)` | 把蓝图状态映射成 M2 所需的 12 个变量（自动带上上一章成绩驱动难度自适应），**调用前过入口预检** |
| `build_planner_prompt(lib, variables)` | 组装 M1 规划 Prompt（同样过入口预检） |
| `next_unlocked_unit(course, progress)` | 找出下一章待渲染的单元 |

```bash
python demo_course_flow.py    # 无需 API Key：用 Few-shot 示例当作 LLM 回复跑通全链路
```

## 模板结构约定

每个角色模板统一采用三层结构，便于程序化组装：

```
[角色设定]  →  身份 + 目标 + 语气
[能力边界]  →  能做什么 / 不能做什么
[输出规范]  →  回答的结构与格式要求
[示例]      →  Few-shot 范例（可选，稳定风格）
```

### 两种 YAML 结构（均已支持）

**新式 `sections`（推荐）**——有序小节，可承载任意自定义字段（如条件分支、难度自适应规则、输出纪律），渲染顺序即书写顺序，不会被静默丢弃：

```yaml
sections:
  - title: 角色设定
    body: |
      你是一名{{学科}}资深教师……
  - title: 能力边界
    do: [能力1, 能力2]
    dont: [禁止事项]
```

**旧式 `system`（兼容保留）**——字段固定为 `role / goal / abilities / restrictions / audience / tone / output_format`，超出的字段会被忽略。仅 `system_base.yaml` 仍在使用。

## 如何新增一个角色

1. 在 `templates/` 下新建 `xxx.yaml`，推荐用 `sections` 结构书写；
2. （可选）在 `fewshots/` 下新建同名 `xxx.yaml` 提供示例；
3. 调用 `lib.build("xxx", {...})` 即可，无需改代码。

> 若一个角色承担多种任务（如教师 Agent），请**按「角色_任务」拆成独立模板文件**，
> 而不是在同一模板里加分支：不同任务的 `output_format` 与 Few-shot 无法共存。
> Few-shot 可在 `build()` 里用字符串指定复用，如 `fewshot="teacher"`。
